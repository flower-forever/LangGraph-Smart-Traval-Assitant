# 旅行助手路线图

目标是一个功能丰富、像携程那样的出行规划助手：分日行程、地图、讲解之外，逐步补上用户对行程的掌控力、信息可信度和部署能力。不抄任何品牌的界面，也不承诺本路线未列出的能力。

**当前阶段不接**：实际预订（机票、酒店）、支付、实时票价与库存查询。这些要接真实交易链路和资质，本轮没有接入；界面不暗示任何站点已预订或可直接下单，也不臆测资质与上线条件。

当前基线：分日规划、Leaflet 地图与路线分级（navigation / straight_line / unavailable）、逐点讲解、本地保存、JSON 备份导入、ICS 导出、停止等待与来源防护已实现。地址身份核对、本地编辑、单日 AI 重规划及独立天气 API/UI 均已提交；天气批次 8e6282d 的 CI 已实际成功。单日地图刷新也已完成 API、预览、显式应用、一次撤销与旧请求隔离；当前本地完整后端 846 项通过、3 项跳过，前端 33 文件 646 项通过，强制类型检查与生产构建通过。以上均为离线模拟与整合验证；真实模型、高德、天气和浏览器联调未测。后续批次 CI 以各自提交的实际结果为准。

## 阶段 B：可编辑行程与约束（进行中，首批开发重点）

用户能改行程，改完地图和文字不再自相矛盾。本地编辑代码完成并通过离线整合验证（前端 25 个文件 523 项测试、强制 tsc 与生产 build 全部通过），与真实服务的联调和浏览器验收未做。首迭代范围（供 Lead 拆解）：

- **本地草稿 + 撤销**：编辑先落在浏览器内存草稿，不动已保存记录；提供撤销到上一个草稿状态。保存仍是显式操作，沿用现有「点了才写 localStorage」语义。
- **可编辑字段**：单站名称/时间/停留时长、站点增删与当日排序。首迭代不改目的城市、天数与 travel_mode 这类触发整体重规划的字段；预算与节奏约束（每天最多 N 站 / 最晚结束时间）放到后续小批。
- **失效与重算**：改名、改地址这类地点身份变化后，该站坐标与受影响路段的 geometry/距离/耗时作废（route_type 回退 unavailable），不得继续画旧路线；只有用户明确触发重算且重算成功，才恢复 navigation/straight_line。只改时间或停留时长时坐标与几何保留，按下一节重做可知性检查。无地图 Key 时保持 unavailable 并如实提示。
- **编辑后的可知时间检查**：只用用户在表单里填写的时间做保守的本地检查，不依赖后端私有时间来源（JSON 里没有）；缺交通耗时或数据未知时不按 0 补齐，也不声称全程可行，只提示需要人工确认。
- **Trip v1 兼容**：编辑产物仍是现有 Trip 结构；不新增必填字段，旧备份照常导入。

首迭代不做：跨天自动调整、编辑后自动写存储。单日重生成由服务端接口承担（阶段 C）。这些边界之外的能力留到阶段 C 或更后。

验收条件：
- 改站点名或地址后，地图上受影响连线立即消失或明确标失效，文字讲解与行程不残留旧坐标结论；只改时间/停留时长时坐标与连线保持不变，时间检查给保守提示。
- 撤销可回到编辑前状态；刷新页面草稿丢失有明确提示（或按实现说明持久化边界）。
- 编辑后的 Trip 能通过现有校验、能保存、能导出 ICS/备份；旧版本前端数据可读。
- 手工核对 + 新增离线单测（失效逻辑、撤销栈、校验）齐全。

其余分批：预算与节奏约束（每天最多 N 站 / 最晚结束时间）、地图/排程同步细节、相应持久化字段设计，在同阶段内后续小批完成，每批单独可验收。

### 小批：每日站点上限偏好（已通过离线验收）

新增每日站点数上限的偏好检查：默认关闭，开关打开后可选生效范围（all_days / changed_days）与上限值（1–8）。它只是编辑会话内的 UI 提示状态：不写入 Trip、不存 localStorage、不发给后端，也不会自动删站；超上限只提示，由用户自行处理。超过 8 站的旧行程照常可读。该偏好不是等价的后端规划约束——后端规划不受它影响。离线独立验收已通过：3 个测试文件 85 项用例全部通过，强制 tsc -b 与生产 vite build 均 exit 0。验收员还修复了一处 forkTripId 切换时偏好从旧草稿泄漏的问题并补了回归测试。CI 结果以推送后的实际运行为准。

### 小批：每天最晚结束时间偏好（已通过离线独立验收）

在每日站点上限之后补充的同类节奏偏好：本地编辑里可设「每天最晚结束时间」（严格 HH:MM，与站点时间同一正则口径，上限取值 0–1439 分钟即 00:00–23:59，24:00 不是合法上限），生效范围同样分 all_days / changed_days（复用 draftChangedDays 口径），默认关闭、会话内有效、不写入 Trip、不存 localStorage、不发给后端，forkTripId 变化即重置，同草稿切天与撤销不误丢设置。

实现为独立纯函数模块 `draftEndTime.ts`（不改 tripDraft.ts，站点上限功能原样）：检查覆盖当天全部站点而非只看末站，按每站填写的开始时刻与已知合法整数停留（0–1440）推算结束下界；开始晚于上限或结束下界晚于上限报结构化 over_limit（下界达到 1440 分钟按「次日 HH:MM」表述，含恰好跨过午夜的次日 00:00，不模 24 冒充当天），边界相等不超；缺停留、旧时间无法解析、旧数据小数 / 超 1440 停留、时钟倒序给结构化 unconfirmed，允许与 over_limit 同天并存；空日不虚构结束，非法上限返回结构化错误；未知交通耗时按未知处理，不按 0 补齐，文案不声称保证按时结束、不宣称营业或预约已核实；没有超限证据的天最多写「按可知填写值未发现超限、仍需人工确认交通」。纯函数不改原对象（deepFreeze 回归），兼容旧宽字段与旧大站数。检查结果只在开关启用时展示：关闭开关、修改上限输入或范围都会清除上一次结果，必须重新点「检查」，禁用状态不冒充已检查结论。

离线独立验收（2026-10-31）：验收员在原作者实现基础上统一了上限合同（0–1439）、把结束下界恰好 1440 归为「次日 00:00」跨日超限并补精确回归、修复了关闭开关后旧结果残留展示、修改输入 / 范围未作废旧结果，以及结果列表 span 内嵌 ul 的 DOM 结构，并同步修订 README 与本节表述。验收回归：`draftEndTime.test.ts` 19 项、`TripDraftEditor.test.tsx` 29 项（原有 26 项断言全部保留），目标 2 文件合计 48 项，4 文件集成套件（含 tripDraft 与 App 整合）112 项全部通过；强制 `tsc -b --force --pretty false` 与生产 `vite build` 均 exit 0。未做真实浏览器验收，CI 结果以推送后的实际运行为准。

## 阶段 C：局部重规划与安全边界

在阶段 B 的编辑骨架上引入受控的重新生成。

服务端部分已就绪：`POST /api/trips/days/replan` 只重生成请求指定的一天，返回独立信封（day / warnings / map_status / parent / source）候选，不写原 Trip、不自动保存；parent 只回显校验，最终版本确认由客户端负责；地图状态用六值 map_status 结构化表达。服务端代码与该前端确认流程（新旧差异预览、确认后合并、一次撤销）已进入仓库并通过离线测试；剩余工作是真实模型与高德的端到端联调验收。

单日地图刷新（POST /api/trips/days/map-refresh）已完成服务端和前端接线：只按请求给定的站点文字重解析坐标并重算相邻路线，返回 typed patch，不调用大模型、不改文字行程；`MAP_REFRESH_TIMEOUT` 总预算默认 20 秒。前端预览后显式应用，使用最新行程与版本校验，可撤销且不自动保存。失败保旧；端点、邻接和方式未变时，本次仅有直线示意不会覆盖旧 navigation，并说明旧记录未重算。已有 51 项后端接口、32 项纯合并、11 项客户端、23 项面板及 6 项 App 整合测试，完整回归结果见当前基线。真实高德和浏览器链路未测，Key 状态以服务端配置为准，不猜配额。

范围：只重规划某一天或某站之后的部分；重规划前先出预览（差异对比），用户确认才覆盖，且只覆盖涉及的天，其他天原样保留；外部模型/高德调用有次数与时间预算，超预算明确停止；用户取消或上游迟到响应不覆盖已确认内容。

验收条件：
- 重规划预览能看到新旧差异；确认前旧行程完整。
- 「只改第 2 天」操作后第 1、3 天内容与地图不变。
- 调用预算耗尽时给明确提示，不静默降级成部分结果冒充完整结果。
- 取消等待后，迟到响应不会覆盖用户当前编辑状态（复用现有停止等待语义并扩展）。

## 阶段 D：可查证的 POI 信息

讲解里的开放时间、票价、天气从「模型说了」变成「有来源」。

范围：为 POI 详情、天气、开放时间/票价增加来源与更新时间记录（来源 URL/接口名 + 抓取时间 + 适用日期）；查不到就标注「未能核实」，不填模型猜测值；界面可见来源标识。先做小范围真实样本评估再扩大，模拟与真实链路分开报告。天气部分：Python 天气 client 已独立实现并通过 82 项离线测试，`GET /api/weather/day` 路由已由 `weather_api.py` 接入 `api_server.py`（只加 include_router，不改原 lifespan），路由与接线另有 28 项离线测试；前端日天气面板已接线并通过离线整合测试，真实 Open-Meteo 样本未跑，旧 OpenWeather MCP 工具也未迁移；fetched_at 记录的是本次获取数据的时间，不是模型预报发布时间。已完成与待接范围分开表述，不写已完成。

验收条件：
- 每条可查证字段能回答「谁说的、什么时候说的」；无法核实的字段有统一标识。
- 未知信息不会伪装成实查结果（对照现有「不编造」边界，扩展到结构化字段层面）。
- 真实样本评估报告（覆盖率和错误率）先于大规模启用。

## 顺序与依赖

A 的质量门槛是所有阶段整合发布的前提。A 验收前可以并行开发独立文件的 B/C 模块（例如只新增文件的草稿逻辑、单日重规划接口），跨文件依赖的改动按依赖顺序串行；未通过 A 的验收就不做整合发布。B 的编辑骨架是 C 的前提；D、E 相对独立，可在 B/C 之间穿插小批推进。每个阶段的每批改动都要走同一流程：实现 → 离线回归 → 独立验收 → 分批提交推送。
